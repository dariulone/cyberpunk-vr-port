# Куда на самом деле пишут PatchCamera и LocateCamera

Полная статическая трассировка (IDA headless `cp2077.i64`) + подтверждение живыми
данными через x64dbg. Дата: 2026-08-13. Imagebase IDA `0x140000000`;
в замеряемом запуске игра была загружена по `0x7FF6CDE80000`.

Короткий вывод: **PatchCamera и LocateCamera работают с ОДНИМ И ТЕМ ЖЕ объектом** —
компонентом камеры. Patch пишет его мировой трансформ, Locate копирует этот же
трансформ в запись микшера камер, микшер складывает записи **со весами** и кладёт
результат в `CameraDirector+0x4C0`.

```
sub_1401D8558  UpdateWorldTransforms(component, bool)        <-- PatchCamera (+0x537)
   пишет component+0xE0 (pos int32x3), component+0xF0 (quat) ; хук ловит запись quat
   -> virtual [vt+0x240](component, component+0x100)  "OnWorldTransformChanged"
   -> рекурсия на детей
                                   |
                                   v  (читает те же +0xE0/+0xF0)
sub_140127F58  CameraComponent::SerializeSetup(out)          <-- LocateCamera (+0x3F)
   виртуальный слот +0x20 интерфейса, лежащего по component+0x120
   заполняет запись CameraSetup (0xA0 байт): pos, quat, FOV, near/far, ...
                                   |
                                   v
sub_14012752C  CameraBlender  (микшер)
   массив записей stride 0xA0; для каждой активной камеры вызывает слот +0x20,
   затем entry+0x90 = вес камеры; результат -> director+0x4C0 (та же структура)
                                   |
                                   v
sub_140126D4C  CameraDirector::Update (слот +0x1D8 vtable 0x142B72EE8)
   ... -> sub_14012752C -> sub_140127404 (читает director+0x4C0 и публикует дальше)
   всё это исполняется в ДЖОБЕ (на живом стеке: sub_1402437B0+0x88 -> sub_140243980+0x79)
```

## 1. Точки хуков в exe (все три паттерна уникальны, 1 совпадение)

| хук | RVA | функция-владелец | смещение в функции |
|---|---|---|---|
| LocateCamera | `0x127F97` | `sub_140127F58` (0x10B) | +0x3F |
| PatchCamera | `0x1D8A8F` | `sub_1401D8558` (0x69B) | +0x537 |
| FinalCamera | `0x785578` | `sub_1407854C0` (0x12CB) | +0xB8 |

## 2. PatchCamera: `sub_1401D8558` — рекурсивный апдейт мировых трансформов

Это не «камерная» функция: это общий узел движка «пересчитать мировой трансформ
компонента и протолкнуть детям». Отсюда и ~16 M попаданий на ~12 k камерных.

- `r15` = родитель: дети `[r15+0xA0]` (stride 0x20), count `[r15+0xAC]`,
  спинлок `[r15+0x8A]`, флаг отложенных `[r15+0xB2]` → `sub_1401C8200`.
- на каждого ребёнка: `rsi` = дочерний компонент; второй handle в записи
  (`[rbx+0x10]/[rbx+0x18]`) — поставщик привязки, у него виртуальный
  `[vt+0xD8](out = pos int32x3 + quat)` = трансформ слота.
- математика: `worldQuat = slotQuat ⊗ localQuat([rsi+0xD0..0xDC])`,
  `worldPos = slotPos + rotate(localPos([rsi+0xC0..0xC8]) / 131072)`;
  `sub_1401D9100` = нормализация кватерниона.
- **записи**: `movsd [rsi+0xE0]` (pos.x,y) · `mov [rsi+0xE8]` (pos.z) ·
  `lea rdx,[rsi+0xF0]` · `movups [rdx], xmm0` ← **инструкция, которую мы патчим**.

Отсюда точные значения наших параметров колбэка:

| в нашем коде | что это на самом деле |
|---|---|
| `cameraState` (rdx) | `component + 0xF0` — мировой кватернион |
| `cameraState + 0x10` (`posA`) | `component + 0x100` |
| `cameraState + 0x20` (`posB`) | `component + 0x110` |
| `ownerState` (rsi) | сам компонент; мировая позиция `+0xE0`, флаги dirty `+0xB0/+0xB1` |

После нашей записи движок сравнивает: старая позиция (`r9d/r10d/r11d`, снятые до) с
`[rsi+0xE0]`, и `sub_1401D9958` (покомпонентное «равно с eps `dword_1431EEE7C`»)
старый quat против нового по `rdx` — то есть **против того, что записали мы**. Если
что-то изменилось или стоит dirty, вызывается `[vt+0x240](component, component+0x100)`
(для класса камеры это `sub_14068E484`). Наша запись поворота сама себе включает эту
нотификацию — хорошо; при абсолютно неподвижной голове нотификация пропускается.

Пять прямых вызывающих (`sub_1401D74FC`, `sub_14068E1F8`, `sub_140E587D8`,
`sub_140E664A0`, `sub_14119518C`) — все имеют один и тот же вид: записать
`+0xE0/+0xF0`, вызвать `[vt+0x240]`, затем `sub_1401D8558` для детей.

## 3. LocateCamera: `sub_140127F58` — сериализатор CameraSetup

Функция вызывается **только через vtable**: это слот **+0x20** интерфейса,
установленного по **object+0x120**. На входе `rcx` = object+0x120, поэтому
`lea rsi,[rcx-0x120]` — это база объекта, а `[rcx-0x40] = obj+0xE0`,
`[rcx-0x30] = obj+0xF0`. **Тот же объект и те же поля, что пишет PatchCamera** —
объект камеры и есть placed component с камерными полями сверху.

Восемь классов камер делят одну реализацию слота +0x20:

| primary vtable | интерфейс @ +0x120 | ctor |
|---|---|---|
| `off_142B031D0` (активная в игре, проверено live) | `142B03130` | `sub_14069CFF0`, `sub_140F2D400` |
| `off_142B03B10`, `off_14307BFD0` | `142B03A70` | `sub_1406A00B4`, `sub_1406A03D8` |
| `off_142B042C8` (базовый) | `142B04228` | `sub_1406A0F44`, `sub_1406A0FE4` |
| `off_142B046A0`, `off_142B049C8` | `142B04600` | `sub_1406A1778`, `sub_1406A1860` |
| `off_142B04D90` | `142B04CF0` | `sub_1406A1938` |
| `off_1431975E0`, `off_14319B810`, `off_1431D6620` | `143197540`, `14319B760`, `1431D6948` | `sub_142537640`, `sub_142586680`, `sub_1428C9F74` |

Раскладка выходного буфера (`rbxPtr` в нашем колбэке), она же структура
**CameraSetup, 0xA0 байт**:

| смещение | источник | смысл |
|---|---|---|
| `+0x00` | `obj+0xE0` (movsd) | pos.x, pos.y — int32 fixed, 1/131072 |
| `+0x08` | `obj+0xE8` | pos.z |
| `+0x10` | `obj+0xF0` (movups) | мировой кватернион |
| `+0x20` | слот `+0x250` = `sub_140126D40` → `[obj+0x410]` | **FOV** (наш FovOverride пишет ровно туда) |
| `+0x24..+0x3B` | слот `+0x258` = `sub_140128748` | 24 байта (refcounted ресурсы `obj+0x2F8/+0x300/+0x308`) |
| `+0x3C`, `+0x40` | слот `+0x270` = `sub_1401280C0` | lerp `[obj+0x15C]`↔`[obj+0x27C]` весом `[obj+0x278]` |
| `+0x4C`, `+0x50` | слот `+0x278` = `sub_140128080` | то же по `[obj+0x164]/[obj+0x284]/[obj+0x280]` |
| `+0x58`, `+0x5C` | `[obj+0x48]`, `[obj+0x4C]` | + флаги в `+0x60/+0x64` |
| `+0x68`, `+0x6C` | `[obj+0x50]`, `[obj+0x54]` | |
| `+0x70..+0x88` | слот `+0x2A8` = `sub_140128070` → `obj+0x178` | 0x1C байт |
| `+0x90` | **пишет вызывающий** | вес камеры (blend weight) |

**Важно для нашего кода**: точка хука стоит между записью `+0x10` (quat) и записью
`+0x20` (FOV). Всё, что движок пишет ПОСЛЕ нас, — это `+0x20` и дальше; `+0x00`
(позиция) и `+0x10` (кватернион) он больше не трогает. Значит наши правки `posFP` и
`quat` в этом буфере доживают до микшера. Существующий комментарий «the engine
refills part of it after we return, so a write here is only half-applied» верен лишь в
том смысле, что буфер — не компонент: через него нельзя достать VRCAM.

## 4. Куда уходит буфер: микшер камер `sub_14012752C`

Найдено программной точкой останова на `sub_140127F58`: адрес возврата `0x1401275FB`.

```
sub_14012752C(rcx = CameraDirector):
  локальный динамический массив записей stride 0xA0 (аллокатор off_142AC0750,
  append = sub_140127DE0)
  for (i = [director+0x54]-1 .. 0):
      вес = [director+0x48][i] + 0x10          ; таблица камер, stride 0x20
      if (вес == 0) continue                    ; камеры с нулевым весом пропускаются
      append(entry)
      camera = [director+0x48][i] + 0x00
      call [[camera + 0x120] + 0x20](entry)     ; <-- LocateCamera
      entry[0x90] = вес
  если записей ровно 1:  sub_1404E9620(director+0x4C0, entry)   ; побайтовая копия
  иначе:
      позиция: (entry[0..8] / 131072) * вес  ->  fixed  ->  += director+0x4C0/+4/+8
      quat:    nlerp (sub_14021136C) с t = вес / (сумма_весов + вес)  ->  director+0x4D0
      всё остальное: entry[X] * вес  ->  += director+0x4C0 + X
```

Итог: **`director+0x4C0` — это та же структура CameraSetup**, поле в поле
(`+0x4D0` = кватернион, `+0x4E0` = FOV, …, `+0x548` = последнее поле).

Живая проверка (игра стоит на бряке, count камер = 1):

| что | значение |
|---|---|
| `component+0xF0` | quat (0, 0, −0.82500, −0.56514) |
| `director+0x4D0` | quat (0, 0, −0.82500, −0.56514) — байт в байт |
| `component+0x410` | FOV 95.0 |
| `director+0x4E0` | FOV 95.0 |
| `[director+0x54]` | 1 (одна активная камера) |

## 5. Выше по стеку

- `sub_140126D4C` = **CameraDirector::Update**, слот `+0x1D8` в vtable директора
  (`0x142B72EE8`): `sub_140126DB8` → `sub_140127B88` → `sub_140127AB8` →
  **`sub_14012752C`** → `sub_140127404` → `sub_14012701C` → `jmp sub_140126F18`.
- `sub_140127404` читает результат обратно (`sub_1401274A4` → `sub_1404E9398` — именно
  на нём срабатывает аппаратный бряк на чтение `director+0x4D0`) в стековый CameraSetup
  и публикует дальше: `sub_14028D4B8(director+0x60, setup)`, затем
  `sub_1404E6974(director+0x400, director+0x230)`.
- Исполняется в джобе: на живом стеке видны `sub_1402437B0+0x88`, `sub_140243980+0x79`
  (job worker, вызывается из `sub_140952CF4`/`sub_140952E94`). Это и есть объяснение
  комментария в PatchCamera про «several engine job threads».

`sub_140126F18` и `sub_140127B88` тоже ходят по `camera+0x120`, но вызывают другие
слоты интерфейса (`+0x78` и `+0x40`), не наш.

## 6. Что из этого следует для порта

1. **Обратная связь реальна и подтверждена структурно**: Patch пишет `component+0xF0`,
   Locate читает `component+0xF0`. Снимок `g_engineCamQuat` (до записи) — единственный
   корректный базис для heading, ровно как и написано в коде.
2. **Наш head-delta в LocateCamera умножается на вес камеры.** При одной активной
   камере вес = 1 и всё 1:1, но во время перехода между камерами (посадка в машину,
   катсцена, любой blend) активны две записи, позиция складывается взвешенно, а
   кватернион идёт через nlerp. То есть на переходах наша добавка масштабируется — это
   отдельный, пока не измеренный источник артефактов именно на переходах.
3. **FOV тоже взвешивается**: `entry+0x20 * вес → director+0x4E0`. Наш `+0x410`
   override корректен только пока вес равен 1.
4. **Почему PatchCamera обязателен для VRCAM**: через микшер проходят только камеры из
   таблицы `[director+0x48]`. Второй view там не участвует, поэтому его трансформ
   можно достать только записью в сам компонент.
5. Буфер микшера лежит в куче (в замере `0x268FEC60580`), поэтому проходит наш
   STACKCAM-фильтр. Отвергаемые стековые буферы приходят от какого-то другого
   вызывающего слота `+0x20` — **не установлено, какого именно** (`sub_140126F18` и
   `sub_140127B88` проверены и исключены: у них другие слоты).

## 7. Кто даёт стековые буферы (STACKCAM) — установлено

Полный список вызывающих слот `+0x20` — 14 сайтов (скан: все инструкции с
immediate `0x120`, затем виртуальный вызов в пределах 12 инструкций). Из них
шесть передают `CameraSetup` **на стеке**, и все шесть распознаются по
предшествующему `sub_1404E96E0` (обнуление CameraSetup):

| функция | что это | буфер |
|---|---|---|
| **`sub_1401274A4`** = слот **+0x2D8** vtable директора | `CameraDirector::GetCurrentSetup(out)` — **главный источник** | `var_98` (холодная ветка `0x141E25327`) |
| `sub_1404E87D0` = слот +0x2E0 vtable директора | второй метод чтения setup | `var_110` |
| `sub_1407FF764` = слот +0x20 **другой** vtable `0x142CE7630` (ctor `sub_1414B6458`) | отдельный класс со своей камерой в `+0x208`, 3 вызова | `var_A0`, `var_130` |
| `sub_14068202C` ← `sub_140682C5C` ← `sub_1406825A4` | | `var_D0` |
| `sub_1428BA40C`, `sub_1428C60B8` ← `sub_141D2E080` | рядом строка `BaseStatusEffect.CyberspacePresence` | `var_110`, `var_130` |

Ложные срабатывания скана (другой интерфейс с тем же слотом, не CameraSetup):
`sub_14081C29C`, `sub_140B474E4`, `sub_140B8B184`, `sub_140669E50`, `sub_14240BEE8`.

**Механизм главного источника.** `sub_1401274A4(director, out)`:

```
захват спинлока director+0x588
rax = [director+0x5A8]                       ; refcount override-камеры
если rax == 0  (обычный случай):
    sub_1404E9398(director, out, r8 = director+0x4C0)     ; отдать blended setup
иначе:                                        ; ХОЛОДНАЯ ВЕТКА
    sub_1404E96E0(&localSetup)                ; занулить CameraSetup на СТЕКЕ
    rcx = [director+0x5A0]                    ; объект override-камеры
    call [[rcx+0x120]+0x20](&localSetup)      ; <-- слот +0x20, стековый буфер
    sub_1404E9398(director, out, r8 = &localSetup)
```

Это **не «transient camera transform»**, как записано в комментарии
`LocateCamera.cpp`, а путь получения setup для **override-камеры директора**
(`director+0x5A0/+0x5A8`) — скриптовые/катсценные камеры.

**Почему STACKCAM молчит.** В текущей сессии в логе `0` строк `[STACKCAM]`, и живая
память объясняет ровно почему: `director+0x5A0 = 0`, `director+0x5A8 = 0` — override
не установлен, холодная ветка не исполняется. Фильтр отключает VR-позу именно для
override-камеры; ориентацию она при этом всё равно получает через компонент
(PatchCamera), так что «второй бейк» убран верно — но по причине, отличной от
записанной в комментарии.

## 8. Тики: замерено на живой игре (72 Гц панель)

| величина | значение | источник |
|---|---|---|
| Present | 71.0–72.5 /с | `[xrrate]`, `[vrik] present` |
| XR cycles / wait / begin / end | 72.0 /с, PAIRED 1:1 | `[xrrate]`, `[xrloop]` |
| display periods на кадр | 1 → 100 % (2+ → 0 %) | `[xrcadence]` |
| **запись камеры MAIN** | **69.2–75.0 /с** (900 записей за 12–13 с) | `PatchCamera: main=` + `[xrcycle]` как секундная метка |
| запись VRCAM | `vrcam = main − 1` | тот же лог |
| **композиция позы (epoch-гейт)** | **72.5 /с = present** | `[vrik] frameEpoch` |
| freshSolve / poseApply | 71.5 /с / 286 /с (4 прохода на solve) | `[vrik]` |
| попаданий в инструкцию PatchCamera | ≈ 88 600 /с (`other` +1 062 929 за 12 с) | `PatchCamera: other=` |
| активных камер | `[director+0x54] = 1`, вес = 1 | живое чтение |

Вывод по частоте: **и запись камеры, и композиция позы происходят ровно раз на кадр**
и совпадают с частотой Present — то есть epoch-гейт в `PatchCamera` работает как
задумано, лишних композиций нет. Цена нефильтрованного сайта видна прямо: ~88.6 k
попаданий в секунду против 72 полезных, отношение ≈ 1230:1.

Фаза: обновление камеры идёт в **геймплейном джобе** (`sub_1402437B0` → … →
`CameraDirector::Update`), то есть до рендера кадра. Поэтому важно, что поза
локируется не «сейчас», а на предсказанное время дисплея
(`AcquireFrameHeadSample` / `LocateHeadPoseAt(aim)`) — иначе staleness блуждает.

Не замерено напрямую: частота вызовов самого `sub_140127F58`. Выведена структурно
(1 вызов на активную камеру за тик директора, а тик директора равен кадру — это и
подтверждают 72 записи MAIN в секунду). Прямой замер: `xr_verbose` даёт строку
`LocateCamera translation` каждые 600 вызовов; `hit_count` в x64dbg MCP для этого
непригоден — он отдаёт устаревшее значение и не растёт между остановками.

## 9. Правильная ли это точка для трекинга шлема

**Ориентация через `PatchCamera` (component+0xF0) — да, и альтернативы нет.**
Это единственное место, где (а) различимы MAIN и VRCAM, (б) запись «прилипает»,
потому что идёт сразу после собственного store движка и до нотификации `+0x240`,
(в) значение попадает в блендер целиком и дальше в view producer, так что culling,
каскады теней и отражения строятся из той же позы.

**Позиция через `LocateCamera` (posFP в буфере) — структурно слабее, три причины:**

1. Добавка попадает в запись микшера и **умножается на вес камеры** (`entry+0x90`).
   При весе 1 (обычная игра) это 1:1, но на любом блендинге камер она ужимается.
2. Позиция и ориентация идут **разными путями**: ориентация — полностью через
   компонент (и участвует в nlerp как одна из камер), позиция — добавкой в уже
   сериализованную копию (× вес). На переходах это рассинхрон «куда смотрим» против
   «где стоим», а не общее замедление.
3. Буфер — не компонент, поэтому VRCAM через него недоступен; отсюда и появился
   отдельный `CyberpunkVR_VrcamHeadTranslation` в `PatchCamera`.

Консистентная альтернатива — добавлять head delta в `component+0xE0` и для MAIN,
ровно как это уже делается для VRCAM. Тогда оба канала проходят один путь и
взвешиваются одинаково. Плата известна и осознана: позиция компонента — это
«геймплейная» голова, её через нотификацию `+0x240` видят IK/физика/звук, и сейчас
они получают несмещённый центр (см. рассуждение в `FinalCamera.cpp` про late IPD
shift). То есть выбор был сделан сознательно — но следствие в виде масштабирования
весом на переходах учтено не было.

## 10. Аудит: какая поза уходит в рантайм (замерено живыми счётчиками)

Счётчики читаются прямо из экспортов `cyberpunkvr_stereo.dll` (x64dbg `symbol_search
CyberpunkVR_Debug*`, затем `memory_read`) — это точнее лога, там нет throttle.

Приоритет источников позы в `OpenXRPresent` (mono submit, `xr_mono_submit=1`):
1. `PopRenderedFramePose()` — очередь, которую наполняет **FinalCamera** (`PoseReadBack=1`)
2. `GetFramePoseForSerial(presentCount)` — метка из `PushRenderHeadPose`
3. `GetRenderHeadPoseForPresent(presentCount, PoseFrameLag)` — ring по лагу
4. `slot.headPoseLocal` — собственный `xrLocateSpace` фрейм-лупа

Замеры (три снимка, флаги на дефолтах: `CamWriteInPatch=1`, `CamComposeAtWrite=1`,
`OneSamplePerFrame=1`, `PoseReadBack=1`, `CamWriteInFinal=0`; ini: `xr_mono_submit=1`,
`xr_render_pose_submit=1`, `xr_pose_lag=1`, `xr_pair_lock=0`, `xr_motion_predict_ms=0`):

| счётчик | значение | что говорит |
|---|---|---|
| `PatchCamMain` / `PatchCamVrcam` | 196 454 / 196 453 | **1:1** — оба глаза патчатся одинаково часто |
| `CamComposed` | 97 929 ≈ Main/2 | **одна композиция на пару глаз** — epoch-гейт работает |
| `CamVrcamFirst` / `CamComposed` | 97 900 / 97 929 = **99.97 %** | композицию почти всегда делает **VRCAM**, MAIN берёт её из seqlock |
| `PoseLocatedAtWrite` / `PoseFromCache` | 97 929 / **0** | всегда свежий `LocateHeadPoseAt(aim)`, кэш не используется ни разу |
| `PoseReadBack` / `PoseExact` | 193 845 / 200 436 = **96.7 %** | метку кадра даёт **FinalCamera-readback** |
| `PoseEstimated`, `FinalNoMatch` | 614, 718 — **не растут** | fallback-пути практически мертвы, идентификация не промахивается |
| `FinalMatch` / `PoseExact` | 194 056 / 200 436, приросты 8 153 / 7 686 = **1.06** | пушей в очередь на 6 % больше, чем попов |
| `FinalTieHits` / `FinalMatch` | 96 693 / 194 056 ≈ **50 %** (сейчас не растёт) | половина идентификаций исторически была неоднозначной |
| `CamNoHmd` | 0 | ни одного кадра без позы |

**Согласованность глаз — измерена и точна.** Из лога `PatchCamera`:
`resid=(0.0483, 0.0432, 0.0000) horiz=0.0648 ipd=0.0648`. После вычитания head-delta
остаётся ровно один IPD в горизонтали (0.0648 против 0.0648) и **0.0000–0.0002 м по
вертикали**. То есть головной сдвиг и разделение глаз не путаются между собой, а
вертикальной диспаратности (которую глаз не сводит вообще) нет.

**Вывод.** Чтение позы и её отправка в рантайм устроены правильно:
- один сэмпл на кадр, локированный на предсказанное время дисплея, общий для обоих
  глаз и для обоих хуков (`AcquireFrameHeadSample`);
- обе камеры получают одну ориентацию, различаются только IPD-сдвигом;
- в `xrEndFrame` уходит поза, **идентифицированная по факту** (readback кватерниона
  через write ring), а не вычисленная из предполагаемой глубины конвейера — это ровно
  тот инвариант, который требует OpenXR («submit must BE the pose it was rendered with»).

### Прямой замер за фиксированное окно — оба заподозренных дефекта опровергнуты

Кумулятивные счётчики сравнивать между собой нельзя: они накопили и те периоды, когда
игра стояла на точках останова. Правильный замер — внешний опросник
(`scratchpad/pose_probe.py`: `ReadProcessMemory` по тем же экспортам, дельты за окно).
60 секунд, 5355 идентификаций, окна по 5 с — все двенадцать окон одинаковы:

```
FinalMatch 89.2/s   PoseExact 89.2/s   PoseReadBack 89.2/s   PoseEstimated 0
push/pop ratio (FinalMatch / PoseExact) = 1.000  -> queue drops ~0.0/s
readback share of exact poses: 100.0%
ties>1: 0 of 5355 matches = 0.0%    NoMatch: 0
AGE  histogram: {0: 5355}      <- идентификация ВСЕГДА находит самую свежую запись
TIES histogram: {1: 5355}      <- кандидат всегда ровно один
compose 71.9/s (vrcamFirst 99.98%)   patch main 89.2/s   vrcam 89.2/s
```

1. **Дропов в очереди нет.** Отношение пушей к попам ровно 1.000 во всех окнах.
   Прежняя оценка «1.06 → ~4 дропа/с» была артефактом сравнения кумулятивных значений.
2. **Неоднозначности нет.** `ties = 1` во всех 5355 случаях, `age = 0` во всех.
   Накопленные `FinalTieHits = 96 693` не растут ни в покое, ни под нагрузкой — они
   относятся к какому-то более раннему состоянию сессии (загрузка/меню), а не к игре.
3. Fallback-пути мертвы полностью: `PoseEstimated = 0` и `NoMatch = 0` за 60 секунд.

### Что замер нашёл вместо этого: четверть кадров рендерится впустую

```
[xrrate] presents 94–95/s | xr cycles 71–73/s | mono submits 71–73/s
         display 13.89 ms = 72.0 Hz | perDisplay 1.00 | perPresent 0.76
[vrik]   present=95.0/s  frameEpoch=95.0/s  reused=23.0/s
```

Три частоты в системе, и они разные:

| частота | значение | к чему привязана |
|---|---|---|
| Present / патч камеры | 94–95 /с | рендер игры, ничем не ограничен |
| композиция позы (`CamComposed`) | 71.9 /с | **XR-цикл** (epoch бампится раз на цикл) |
| submit в шлем | 71–73 /с | панель 72 Гц |

`perPresent = 0.76` — на один Present приходится 0.76 XR-цикла, то есть
**95 − 72 ≈ 23 кадра в секунду рендерятся и выбрасываются** (~24 % работы). Тот же
23 стоит в `[vrik] reused=23.0/s`. Следствие для позы: 23 кадра в секунду строятся с
композицией предыдущего XR-цикла. Артефакта это не даёт — readback метит каждый кадр
его собственной позой (`age = 0`, 100 %), — но GPU/CPU-время тратится, а «1 рендер =
1 submit» было бы и дешевле, и фазово стабильнее. Ограничение кадров до частоты панели
проверяется отдельно и здесь не измерялось.

`FinalCamera` как **писатель** камеры (`CamWriteInFinal=1`) — отдельная история и по
умолчанию выключен; как **читатель** он уже несёт 96.7 % меток и работает без промахов.

## 11. Что движок делает с мышиным вводом (и почему занять сглаживание у него нельзя)

Проверено по строкам exe и по загрузчикам параметров в `render_camera_RE`.

Конфиг чувствительности камеры грузит `sub_1428A7EF8` (и `sub_14060B098` для
`fppCameraParamSets`). Полный набор того, что вообще применяется к вводу:

| для мыши | для стика |
|---|---|
| `SensitivityConfig.Base.mouse` — множитель | `SensitivityConfig.Base.pad`, `UserFPP.padX/padY` |
| `cameraPlaneSettings.CameraCurves.sensitivityCurveName` → `base\gameplay\curves\camera_curves\sensitivity_mappings.curveset` — нелинейная кривая | `UserFPP.padMaxAcceleration`, `fullStickRampTime`, `fullStickBonusYaw/Pitch`, `fullStickBonusDelay`, `fullStickAdsBonus*`, `Base.fullStickThreshold` |

**Вся временная механика (ускорение, рампы, задержки) существует только для стика.**
Для мыши это множитель и кривая — обе операции безынерционные, кадр в кадр.

Что ещё в камере похоже на сглаживание, но им не является:

- `.yawRubberBandInputDamping` / `.pitchRubberBandInputDamping` — демпфируют ввод только
  когда камера натянута к пределу относительно тела (`yawRubberBandLimit`,
  `yawRubberOnStretchSlowdown`, `yawRubberReturnMultiplier`). Это ограничитель, а не фильтр.
- `.fovSmoothingDuration`, `.maintainFovSmoothingDuration` — сглаживают FOV, не позу.
- `.headingLocked`, `.headingResetSpeed`, `.headingResetTimeout`,
  `.headingResetOnlyWhenMoving`, `.maintainWorldSpaceHeading` — авто-возврат heading к
  направлению тела. Это и есть «body yaw follower», уже известный как источник снапов.
- `.clampSmoothing`, `.directionSmoothFactor`, `.offsetSmoothing*`, `.radiusSmoothFactor`,
  `.smoothSpeedDampFactor` — TPP-камера, транспорт, оффсеты. К FPP-позе не относятся.

Вывод: **позу FPP-камеры движок не фильтрует вообще**, поэтому «отдать сглаживание
движку» нечему. Это и логично — мышь даёт событийные дискретные шаги без шума, а шум
приходит от трекера, которого движок не знает. Фильтр обязан жить на нашей стороне.

## 12. Итог: что стоит в пути позы сейчас

| параметр | значение | что делает |
|---|---|---|
| `CyberpunkVR_PredictFilter` | **3** | lerp с фиксированной константой на позе ВИДА |
| `CyberpunkVR_HeadFilter` | **3** | тот же lerp на кэше `m_pos*/m_ori*`, который читает VRIK |

## 13. VRIK: что движок читает, когда рисует скелет (IDA + живой watchpoint)

Хук стоит на `sub_14017DDB4` (RVA `0x17DDB4`, жёстко, без паттерна). Это **не** «применение
анимации», а **копировщик поз**: он переливает подмножество костей из результата
анимграфа в целевой буфер по таблице переиндексации.

```
rax = [a2+0x38]          ; poseDesc      (в коде: a2[7])
r10 = [rax]              ; boneBuf       (poseDesc[0])   <-- наш детур пишет сюда
r12 = [rax+0x18]         ; trackBuf      (poseDesc[3])   <-- по нему опознаётся риг игрока
r11 = [a3+0x30]          ; источник — выход графа
цикл: movups/movdqu ×3 = 48 байт на кость
```

Живой замер (hw watchpoint на чтение/запись кватерниона hips = `boneBuf + 2*48 + 16`,
условие «cip вне нашей DLL», риг игрока отфильтрован по `trackBuf == g_PlayerTrackBufB`):

| адрес | функция | что делает |
|---|---|---|
| `0x17DE39` | `sub_14017DDB4+0x85` | сам копировщик, **пишет** кость |
| `0x17E027` | **`sub_14017DFD4+0x53`** | **геттер кости**: читает 48 байт (`[rax]`, `[rax+0x10..0x1C]`, `[rax+0x20]`) по индексу |
| `0x1E1DAC` | `sub_1401E10BC+0xCF0` | вызывает геттер и **копирует кость в ДРУГОЙ буфер**: `movdqu [r14+rsi+0x10], xmm0` |
| `0x1DC514` | `sub_1401DC460` | композиция трансформов (`addsubps`/`shufps` = произведение кватернионов), **пишет** `[r11+0x10]` |

Вызывающие геттера `sub_14017DFD4`: `sub_14017DDB4+0x197` (сам копировщик, в конце),
`sub_1401D2DB8` (×2), `sub_1401E10BC` (`0x1E1DA7`, `0x1E2505`).

**Главный факт: рендер читает не наш буфер.** `boneBuf` — это локальные позы; движок
прогоняет их через геттер и складывает в производный буфер (`sub_1401E10BC`), а
`sub_1401DC460` компонует трансформы. Значит корректность нашей записи определяется не
только тем, что мы пишем последними внутри `pose-apply`, но и тем, попадаем ли мы **до**
построения производного буфера — а он строится в том же `sub_1401E10BC`, который зовёт
и копировщик (`0x1E1BB8`), и геттер (`0x1E1DA7`).

Что при этом ОПРОВЕРГНУТО измерением: движок не перетирает наши кости между проходами —
`engine moved our bones by up to 0.0 mm ... in 0 of 444 replay passes`. Батчи:
`151/с при 72 Гц`, внутри батча проходы с зазором < 0.5 мс, между батчами ≥ 10 мс.

### Проверка точки записи: геттер читает ИМЕННО наш буфер

`sub_14017DFD4(rcx, rdx = out, r8, r9d = boneIdx)`, начало декодировано живьём:

```
movzx eax, [rcx+0x10]     ; количество костей
cmp   r9d, eax            ; bounds check
mov   rsi, [r8+0x10]      ; таблица индексов
mov   r14, [rcx]          ; <<< r14 = [rcx] = boneBuf
rax = r14 + idx*48        ; и дальше читаются все 48 байт кости
```

Вызов на `0x1E1DA7` передаёт `rcx = [rbx+0x38]` — тот же poseDesc, у которого `[0]` =
`boneBuf`, `[0x10]` = количество (живьём: 0x32 = 50 костей). То есть **движковый читатель
берёт ровно тот буфер, в который пишет наш детур**; теневого буфера локальных поз нет, а
`0x1E1DAC` копирует в производный буфер уже нашу кость.

**Следствие: точка записи верна, переставлять её не нужно.** Гостинг приходит не от того,
что нас читают мимо, а от того, ЧТО мы пишем — от источника позы для solve.

### План чистки (пункты, каждый отдельно собираем и оцениваем)

Ключевой факт, делающий чистку возможной: `AnimPose.cpp`, `src/Anim/*` и `OpenXRManager`
компилируются в ОДИН `CyberpunkVR_Stereo.dll` (см. комментарий «ONE PLUGIN, NOT TWO» в
CMakeLists). Значит shared memory в пути solve — пережиток эпохи двух плагинов.

1. `snapEvent`-ветка replay + чтение `[147]` — удалить (делалась под snap-turn, признан неверным).
2. `pair lock` (`m_pairLockHands`, `m_pairLockHmdOri`, `xr_pair_lock`) — удалить, AER нет.
3. **Выполнено для camera/model transform:** ориентация solve берётся напрямую из
   `OpenXRManager::Get().AcquireFrameHeadSample()` и текущих engine body yaw/game pitch. Это тот же
   frame latch, из которого позже `PatchCamera` строит вид. Позиция берётся не из позднего
   `g_lastLocate*`, а из seqlock-снимка относительной пары `(cam-entity)` одного `SetVRPlayerYaw`.
   Остальные чтения shared для контроллеров/рук пока сохраняются и чистятся отдельно.
4. Запись в shared СОХРАНЯЕТСЯ (её читают CET/Lua и redscript), убирается только ЧТЕНИЕ
   из shared внутри solve.

Важная поправка к формулировке «VRIK должен сидеть на FinalCamera»: камеру мы пишем не там
(`CamWriteInFinal = 0`), `FinalCamera` только опознаёт позу для метки, и её результат
появляется ПОСЛЕ анимации — для solve он недоступен по времени. Эквивалент, причём более
сильный, это `AcquireFrameHeadSample` (пункт 3).

### Исправленная фазовая ошибка VRIK (2026-08-21)

Animation solve выполняется раньше `LocateCamera`. Поэтому прежняя формула
`g_lastLocatePosFP(N-1) - CyberpunkVR_PlayerEntityPos(N)` не была относительной позой камеры: в ней
оставался один полный кадр мирового движения игрока. При движении вперёд старое тело обычно
оказывалось за глазами, при движении назад — перед ними; скорость бега увеличивала ошибку. Та же
ошибка по кватерниону оставляла head bone на один camera sample позади поворота HMD.

Теперь `VRIK_ComputeCamModel` использует согласованный снимок `(camQ, entityQ, cam-entity)` одного
CET-пуша для model-space позиции, где мировая трансляция и yaw взаимно сокращаются, и текущий
`AcquireFrameHeadSample` только для ориентации head bone. Руки, arm axes и model↔world-конвертеры
получают отдельно возвращаемый `outPairedRot` из согласованного camera/entity-снимка — стабильный
base frame, который ожидает существующая controller-композиция. Смешивание его данных со свежей
головой оставляет движение HMD между двумя моментами прямо на рычаге руки.
`CyberpunkVR_VrikSplitHeadHandRot=0` воспроизводит смешанный путь
для live A/B, не отключая исправленный якорь тела. `g_lastLocate*` остаётся полезным
readback/диагностическим зеркалом, но больше не является входом animation solve.

### Дополнение: устранение Lua-clock из позиции рук (2026-08-21)

Предыдущий coherent snapshot исправлял смешение `camera(N-1)`/`entity(N)`, но сам приходил с
частоты CET/Lua и проходил через slew-лимитер. Это давало лестницу в `camModelPos`: повторённое
значение на одном animation solve и двойной шаг на следующем. `[vrikshake]` локализовал первый
общий рывок обеих рук в anchor при спокойных controller samples.

Текущий primary path публикует камеру из `LocateCamera` и сохраняет engine entity transform в
`BodyYawFollowTick`. Пара принимается только как `camera(N-1)-entity(N-1)` с одинаковым
`g_VrikFrameEpoch`; поля обоих межпоточных snapshot атомарны. `VRIK_ComputeCamModel` предпочитает
эту пару, а Lua snapshot использует только если нативная пара для текущего epoch недоступна.
Позиция gizmo-target обеих рук теперь непосредственно использует нативный `handAnchor`, поэтому
скрытый второй Lua-путь через `VRIK_ResolveViewPos` больше не возвращает Lua-лестницу в IK target.

Это не закрывает отдельный shared-slot аудит view quaternion/offsets: `[104..107]` защищены
seqlock `[143]`, но старый `SharedPose`-потребитель копирует их под `[127]`. Его нельзя смешивать
с проверкой нативного anchor.

## 15. Рендерная половина: рендер-камера → view-state → temporal (TAA/DLSS/FSR)

Реверс этой половины уже был сделан и лежит в репозитории — `render_camera_RE/`
(`README.md`, `analysis/ANALYSIS.md` §11, `analysis/camera_analysis.md`,
`render/nodes/nodes_index.md`, `render/A_view_orchestrator.md`). Формат таблицы нод —
`node | work_fn | node-vtable | ctor | getter`, и **work-fn = `qword[дескриптор − 0x08]`**,
где дескриптор — это 0x30-байтная запись в `.rdata` (для TXAA `0x142B935E8`). Колонка
`getter` (`0x140CF2A3C` у TXAA) — это провайдер имени/хэша: там `_Init_thread_header` и
строка `"CRenderNode_ApplyTXAA"`, работы пасса в ней нет.

### 15.1 Единственный писатель: `sub_140788A9C` = work-fn `CRenderNode_SetStreamlineConstants`

Выполняется только если `*(qword_143427C00 + 0x4658) != 0` — это **один общий view-state на
рендерер**, не на глаз. Камера берётся из контекста ноды: `cam = *(a2 + 0x18)`; вторым
источником идёт `a1` (параметры кадра) — оттуда приходит джиттер.

Что читается из рендер-камеры (та же структура, что читает `FinalCamera`):

| поле камеры | что это | куда уходит |
|---|---|---|
| `cam+0x70/0x74/0x78` | позиция, int32, множитель `dword_1431EEE78` | `vs+0x1A0..0x1A8` |
| `cam+0x90`, `cam+0x98` | два int | `vs+0x1D8`, `vs+0x1DC` |
| `cam+0xB0/0xB4` | размеры вьюпорта | `vs+0x1D0/0x1D4` |
| `cam+0xC0 / +0xD0 / +0xE0` | строки матрицы ориентации | матрицы вида |
| `cam+0x2C0`, `cam+0x2D0`, `cam+0x2E0` | три float3 (базис) | `vs+0x1B8`, `vs+0x1C4`, `vs+0x1AC` |
| `cam+0x3E0`, `cam+0x3E4` | два float (второй с инверсией знака) | `vs+0x1E0`, `vs+0x1E4` |
| `a1+0x8 / +0xC / +0x10` | джиттер и его масштаб — **не из камеры** | `vs+0x1E8/0x1EC` |

Что пишется в view-state (`vs`):

```
vs+0x20..0x50   матрица M            (4 строки movups)
vs+0x60..0x90   inv(M)               (lea rcx,[rdi+60h] → sub_1401E3EE8, обращение 4x4)
vs+0xA0..0xD0   матрица N
vs+0xE0..0xF0   обращение N          (sub_1401E3EE8)
vs+0x100/0x110  ещё две строки
vs+0x120..0x190 производные матрицы  (двойная точность sub_1429ED740, inv-by-det sub_14078A214)
vs+0x1A0..0x1CC позиция + три вектора базиса
vs+0x1D0/0x1D4  размеры;  vs+0x1D8/0x1DC два int;  vs+0x1E0/0x1E4
vs+0x1E8/0x1EC  ДЖИТТЕР
vs+0x1F0        флаг;  vs+0x1F2 |= (sub_14078A124);  vs+0x1F3 = 1 (valid)
```

Важное отрицательное наблюдение. `sub_14028DB28` (копия ~904-байтного состояния камеры)
вызывается **дважды** — на `0x140788DAF` и `0x14078918D` — и я проверил аргументы: оба раза
источник это `cam+0x70` **одной и той же камеры** (`rsi = [r14+0x18]`, и второй раз
`rdx = [r14+0x18] + 0x70`), а приёмник — временный буфер на стеке для сборки матриц.
То есть **отдельного объекта «камера предыдущего кадра» здесь нет**, и версия «движок
снимает prev до нашей записи» опровергнута: снимать нечего, prev живёт не в камере.

### 15.2 Хвост: `sub_14078933C` — блок констант Streamline

Вызывается из `sub_140788A9C` последним (`0x1407892D7`) и собирает структуру констант по
адресу `vs+0x200`, после чего дёргает `slGetNewFrameToken` и
`slSetConstants(vs+0x200, token, vs+0x478)`. GUID фичи
`0x3454215E96C451A6_49026D0BF03AF81A`.

```
vs+0xA0..0x110  →  vs+0x220..0x290     (8 строк = две матрицы 4x4)
vs+0x20..0x90   →  vs+0x2E0..0x350     (8 строк = две матрицы 4x4)
vs+0x1E8 (пара float, джиттер) → vs+0x368
vs+0x1A0/0x1A8/0x1AC/0x1B4/0x1B8/0x1C0/0x1C4/0x1CC → vs+0x378/0x380/0x384/0x38C/0x390/0x398/0x39C/0x3A4
vs+0x1D0/0x1D4/0x1D8/0x1DC → vs+0x3A8/0x3AC/0x3B0/0x3B4
флаги из vs+0x1F0/0x1F2/0x1F3 → vs+0x3BD/0x3BE/0x3BF (через setnz/setz)
```

Внутри блока есть **пропуски** — `vs+0x2A0..0x2DF` и `vs+0x358..0x367` этой функцией не
пишутся. Именно они и несут «предыдущий кадр»: там остаётся то, что положил предыдущий
вызов, а Streamline получает всю структуру целиком. То есть история строится не из
отдельной prev-камеры, а из того же самого блока на кадр раньше.

Три гейта на входе: `vs+0x43B` и `vs+0x43C` (обе должны быть непустыми) и

```
if (byte_1448FF9F4 == 0 && frameIdx == [vs+0x4A0]) return;   // frameIdx = [vt20(node[0]) + 0x1A0]
...
[vs+0x4A0] = frameIdx;                                        // 0x1407896AA, в самом конце
```

`byte_1448FF9F4` во всём exe только СРАВНИВАЕТСЯ (12 ссылок, ни одной записи по xref) —
похоже на флаг режима сборки, который в игре 0. Значит гейт работает.

**Но гейт закрывает ТОЛЬКО push в Streamline, а не запись view-state.** Это важная поправка,
и её дало прямое наблюдение в Nsight: джиттер и motion vectors у каждого вида РАЗНЫЕ. Так и
должно быть — `sub_140788A9C` это work-fn ноды фрейм-графа, она выполняется **на каждый вид**,
и всё, что она пишет (`vs+0x20..0x190` матрицы, `vs+0x1A0..0x1CC` позиция и базис,
`vs+0x1E8/0x1EC` джиттер), пишется без всяких гейтов, из камеры именно этого вида. Глобальный
CB каждого вида собирается, пока view-state держит значения этого вида, — отсюда и разные
джиттер/векторы в кадре.

Под гейтом остаётся один `slSetConstants` на кадр. Что это означает для второго глаза при
включённом DLSS/FG — вопрос к внутренностям Streamline (`ApplyDLSS` зовёт `sub_14290FDA4` с
хэндлом view-state, и что тот пушит сам, здесь не видно), поэтому дефектом это называть
преждевременно. Прежняя формулировка «второй вид не получает своих матриц и джиттера» была
неверной: она распространяла гейт на всю функцию.

### 15.3 Кто это потребляет

- **`CRenderNode_ApplyDLSS`** (work `sub_14037D5C4`) — читает `qword_143427C00+0x4658` и
  передаёт view-state **как хэндл** в `sub_14290FDA4` (дважды, с id ресурса 3 и 2). Своей
  камеры у ноды нет: она оценивается на view-state.
- **`CRenderNode_ApplyTXAA`** (work `sub_140768510`, 0x9FE) — гейт по биту фичи `0x14`
  (`sub_14023AF5C`), затем семь ресурсов через `sub_1401F0F80` из контекста ноды. Матрицы
  сама не читает — берёт из привязанных глобальных констант.
- **`CRenderNode_BuildTemporalInvalidationMask`** (work `sub_140156F80`).

### 15.4 Что из этого следует для трейла

У temporal нет независимой камеры. Всё, чем он пользуется — матрицы, джиттер, позиция,
базис, размеры — производится `sub_140788A9C` из рендер-камеры, то есть **ниже нашей записи
по потоку**, а «предыдущий кадр» — это тот же блок констант на кадр раньше. Значит наша
запись не может рассинхронизировать current и prev между собой: они оба наши.

Отсюда вывод, который согласуется с замером «в буфер и в компонент дают одинаковый трейл»:
если temporal и даёт двойник, то не из-за камеры, а из-за пикселей, которые сдвинулись без
соответствующих motion vectors — то есть из-за скелета (prev-матрицы костей), а не из-за
вида. Камерная половина цепочки на этом закрыта.

Записать сюда же, чтобы не искать снова: писать в view-state (`vs+0x1D0..0x1F3` и матрицы) —
это та же стадия, что `FinalCamera`, только чуть выше. Она **ниже** отсечения, каскадов
теней и distant-пассов, поэтому даёт тот же класс артефактов («здания двигаются»), и как
точка записи для нас непригодна, даже несмотря на то что `ANALYSIS.md` §12 предлагает её
для per-eye IPD.

## 16. Та же цепочка для VRCAM (замерено 2026-08-28, x64dbg + IDA 9.2 на cp2077.i64)

Раздел собран по прямому запросу: «нужно посмотреть всю стадию для VRCAM как это у MAIN, с 100%
точностью». Каждый пункт помечен тем, чем он установлен. Где не установлено — так и написано.

### 16.1 Что такое компонент VRCAM

`entRenderToTextureCameraComponent`, висит на игроке. В живом списке компонентов игрока их 62 штуки —
по одной на авторскую резолюцию (`vrcam_<W>x<H>`, в брейндансе `vrcam_braindance_<W>x<H>`), включена
одна. Опознание объекта на 100%: **`comp+0x00` (vtable) == `exe+0x307BFD0`** — сверено дважды в двух
сессиях, на разных адресах объекта.

    comp+0x00           vtable, == exe + RTT_HOST_VTABLE_RVA (0x307BFD0)
    comp+0xE0           позиция, int32[3]
    comp+0xF0           кватернион            <-- то, что пишет PatchCamera
    comp+0x100          мировая матрица       <-- то, что отдаётся вниз (OnWorldTransformChanged)
    comp+0x258/0x25C    ширина/высота выбранной резолюции
    comp+0x260          КЛЮЧ ВИДА, сверяется с g_vrcam_ctx_key
    порт держит указатель в g_vrcam_comp

### 16.2 Стадия 1 — идентична MAIN

    sub_1401D8558  UpdateWorldTransforms(component, bool)        <-- PatchCamera
       пишет component+0xE0 (pos int32x3), component+0xF0 (quat)

Аппаратная точка на запись по **VRCAM**`+0xF0` дала ту же тройку, что у MAIN:

    1) движок      трамплин +0x…021A   (перенесённая movups [rdx], xmm0)
    2) мы          cyberpunkvr_stereo.dll+0x213C4
    3) мы          cyberpunkvr_stereo.dll+0x213C4

**Движкового писателя ПОСЛЕ нас нет ни одного** — проверено и для MAIN, и для VRCAM. Именно это делает
`PatchCamera` работающей точкой: она идёт сразу за собственной записью движка.

Важно не перепутать при повторном замере: адрес `+0x…021A` лежит в НАШЕМ трамплине, но это инструкция
движка. Раскладка трамплина (из установщика `InstallPatchCameraHook`), сайт — паттерн
`0F 11 02 | 80 BE B1 00 00 00 00 | 89 45 88`, `replaceLen = 10`, где `0F 11 02` и есть движковая
`movups [rdx], xmm0`:

    push rax; mov rax, g_telemetry+kPatchTelemetryOffset
    inc dword [rax]; mov [rax+0x08], rdx; mov [rax+0x10], rsi; movups [rax+0x18], xmm0; pop rax
    movups [rdx], xmm0            <-- ОРИГИНАЛЬНАЯ ИНСТРУКЦИЯ ДВИЖКА, перенесённая сюда
    pushfq; push rax,rcx,rdx,r8,r9,r10,r11,rbp; sub rsp,0x40; movups [rsp+00/10/20/30], xmm0..xmm3
    mov rbp,rsp; and rsp,-16; sub rsp,0x20
    mov rcx,rdx (camera state); mov rdx,rsi (owner state); call OnPatchCameraCallback
    ...восстановление...; cmp byte [rsi+0xB1],0; jmp назад на site+10

В регистрах на сайте: **`rdx` = component+0xF0, `rsi` = component**. Сходится с логом порта
(`PatchCamera state @…30100 owner=…30010`, разница 0xF0).

### 16.3 Стадия 2 — у VRCAM ОТСУТСТВУЕТ

    sub_140127F58  CameraComponent::SerializeSetup   \
    sub_14012752C  CameraBlender                      >  только MAIN
    sub_140126D4C  CameraDirector::Update            /

Аппаратная точка на **чтение-запись** по `comp+0xF0` не дала ни одного движкового ЧИТАТЕЛЯ — только
наши (`stereo.dll+0x21322`). Совпадает с §6.4: в микшер идут лишь камеры из таблицы `[director+0x48]`,
второго вида там нет. То есть у VRCAM нет сериализатора камеры этого класса вообще.

### 16.5 Почему в собственный путь VRCAM писать нельзя

**`sub_1404FBAFC` не копировщик трансформа.** По псевдокоду она работает с `a1+488/504/512/528/536`
(ресурсы RTT) и `a1+600/604` (размеры); полей `+0xE0/+0xF0/+0x100` не касается. Первым делом зовёт
`sub_140665054(a1, a2)`, остальное условно от результата. Как точка записи ориентации не подходит, и
отдельно: попытка вести запись через view-create уже делалась и давала лаги.

**Трансформ VRCAM выводится из родителя, по реакции на MAIN.** Слот `[vtable+0x240]` RTT-компонента —
это `sub_14068E54C`. С условием на наш компонент он **не сработал ни разу**, без условия срабатывает
постоянно, потому что `onWorldTransformChanged` привязан в ассете к `camera`: любое изменение камеры
MAIN (голова, мышь) дёргает его. Это и объясняет записанный ранее отрицательный результат — «a write
placed outside its own update does not survive» / «stopped VRCAM tracking altogether».

**Вывод.** Единственная точка, где запись в VRCAM выживает, — сразу за собственной записью движка, то
есть `PatchCamera`. Это не «единственная оставшаяся», а доказанно последняя по порядку.

### 16.6 Что НЕ установлено

- **Кадры джоба над `sub_14079ACA0`.** У MAIN они известны (`sub_1402437B0+0x88` -> `sub_140243980+0x79`).
  У VRCAM штатный обход стека даёт один кадр; ручное сканирование выдало кандидатов RVA `0x1F3587`,
  `0xA2BADA`, `0x1EC60F`, `0x1EC521`, но отличить живые кадры от мусора на стеке без указателей кадров
  нельзя, поэтому в схему они не внесены.
- **Звено между `comp+0x100` и `src` построителя.** Кто именно копирует мировую матрицу компонента в тот
  стековый источник — не пойман. Точка на `comp+0xF0` движковых читателей не дала, значит вниз уходит
  `comp+0x100`, и следить надо за ней. Источник — стековый временный объект `sub_1404E4AFC`, так что
  заполняет его она сама; из её вызовов на роль копировщика похожи `sub_14028DB28` (0x4E50E0, копия
  состояния камеры) и `sub_1404E42A0` (0x4E5175), но это ПРЕДПОЛОЖЕНИЕ, не замер.
