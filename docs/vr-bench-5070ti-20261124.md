# VR bench on the RTX 5070 Ti: C++ (branch cpp) against Rust (main), 2026-11-24

This machine: RTX 5070 Ti 16 GB. The C++ build is main before the Rust move (f7a824dd5, now branch `cpp`; the DLL
built on HOME-PC, c74de31f, with its matching PDB). The Rust build is main (4091fcd78 + the static-call cache below).
The runs use one game folder and the same save (ManualSave-491). They use the same bench simulator (OpenXR Simulator
with head_trajectory, Quest 3 profile, 90 Hz target) and the same head trajectories. Settings are also the same:
the player's C++ `vrport.ini` plus `xr_engine_stereo=1 xr_depth_submit=1 xr_fps_cap=1 xr_framegen_overlay=1`, with
frame generation, OSR, AFW, foveated DLSS, VRS and the hidden area off. Both use the player's
`vrport-launcher.ini` (2648x2864, hmd_type=2). The driver is `tools/vr_bench/ab_builds.py run`. On `still`, ETW CPU
sampling is on in every run, so that row is slower than the others.

Results: `build/vr-bench/20261124-144811-ab5070eq-cpp`, `20261124-145322-ab5070eq-rust` (before the fix),
`20261124-150421-ab5070cache-rust` (after).

## What made the Rust build slower (and the fix)

Before the fix, the Rust build's game thread took 26.2 ms of CPU per frame, against 18.6 ms for C++. The GPU waited
11 ms a frame for it. The top port function was `cvr_rust::mechanics::lobby_rtti::static_call` (1.94 ms of its own
time), with `memchr` / `from_utf8` behind it. This is the Rust replacement of the Lua mods' CET calls (`Class.Static(...)`),
and 36 mechanics call it every tick. Each call did three costly things:

- When the class had no fitting static of its own, `pick_static` walked every global function of the game. It read
  each one's name from the game's name pool (time spent in `Cyberpunk2077.exe`) and split it at `;`. Nothing was cached.
- `fits` / `run` / `Val::num` built a `String` of each parameter's type name to compare it.
- `breadcrumb` formatted its text and read `CVR_MENU_TOUR` from the environment block, under the process lock.

The fix is in `rust/crates/cvr-ffi/src/mechanics/lobby_rtti.rs`:

- `resolve_static` caches the function a (class, name, argument kinds) call picks. A miss is looked up again after 2 s,
  because the scripts are still registering during the first ticks. A non-static the call refuses is cached as refused.
- Type names are compared as CName hashes (`T_FLOAT`...).
- `breadcrumb` takes a closure and reads the environment once.

After the fix, the game thread takes 16.6 ms per frame and the whole process 164.5 ms, against 194.7 ms before and
178.0 ms for C++.

## Bench pitfalls found on the way

- The frame rings vr_bench reads (`CyberpunkVR_FrameRingCpu/Gpu`) are filled only with `xr_framegen_overlay=1`.
  Without it every window reads "STALL: 0 frames". ab_builds now sets the key.
- The two installs keep their own `vrport-launcher.ini`. The fresh Rust package had 2080x2104 / hmd_type=0, while the
  player's C++ install had 2648x2864 / hmd_type=2. ab_builds now gives both runs the C++ file. `ab_builds.py
  adopt-settings` carries the player's port settings into the Rust install: launcher, VRIK, calibration, FBT rigs and
  holster places.
- The installed C++ DLL had a stale PDB (same GUID, age 7 against the DLL's 14), so dbghelp found no symbols
  (`g_menuModeValue`). The bench used HOME-PC's clean f7a824dd5 build instead.
- Once, the first launch of the freshly installed Rust build got System32's powrprof.dll instead of the port's loader:
  no port, a flat game. Three later launches, one right after the same aside-and-back rename, loaded it. The cause is
  not found. ab_builds now records `port_started` from `cyberpunkvrport\log\loader-trace.txt`.
