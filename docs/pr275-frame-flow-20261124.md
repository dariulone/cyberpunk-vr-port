# PR #275 (#243: the headset at ~1 fps once the GPU falls behind) on the Rust main, 2026-11-24

PR #275 is built on the C++ code (src/Runtimes/OpenXRCapture.cpp, OpenXRFrameLoop.cpp) and was play-tested on
release 0.2.45. It makes two changes:

1. **`m_monoOlderFrame`.** A third published capture. When both the newest and the previous capture are still on the
   GPU, the submit takes the older one if it is finished and not shown yet.
2. **`kMaxHoldNs` 1 s -> 10 s.** The time the last frame may be resent before the cycle goes out empty (no layers).

The Rust main has neither, but it has main's 8255f379b (2026-11-17, after 0.2.45): CaptureFrontier's
ProtectPrevious / ReplacePrevious, in `rust/crates/cvr-render/src/xr_capture_state.rs`. An unpresented previous capture
is kept until it is presented, and only a *finished* newest replaces it. The GPU runs its queue in order, so the kept
frame is always the oldest one not yet shown, and it is the first to finish. That closes the loop the PR describes
("both selectable captures perpetually unfinished") without a third frame.

## Measured (tools/vr_bench/frame_flow.py, RTX 5070 Ti, ManualSave-491, engine stereo, DLSS)

Each run has three phases. First, 30 s GPU-bound: the launcher's per-eye size raised with custom_res=1, and the GPU
2+ frames behind on every cycle ("notDone" on every one). Then 8 pause-menu Esc presses, 4 s apart (the PR's trigger).
Then 20 s of recovery. The counters are the port's own (XrProjectionCycles, XrRepeatCycles, XrResubmits, XrEmptyEnds,
XrCaptureNotDone, XrCapturePrevious, DebugCapOk) with RuntimeDiagnostics on, read once a second.

| runtime | build | frame gen | captured | shown new | empty ends | seconds without a new picture | worst second after a menu |
|---|---|---|---|---|---|---|---|
| OpenXR Simulator, 3600x3900/eye | main | off | 4110 | 4079 | **0** | 1 (the first) | 18 new |
| SteamVR 2.18.4 null driver, 2648x2864/eye | main + LUID fix | off | 5647 | 5626 | **0** | 0 | 28 new |
| SteamVR null | main + LUID fix | on | 4105 | 4097 | **0** | 0 | 15 new |

In the GPU-bound phase every captured frame reached the runtime: 1262 of 1262 on the simulator (42/s) and 2040 of
2040 on SteamVR (66/s). On almost every cycle the newest capture was still running, and the previous, finished one
went out instead. After a menu closed, the rate was back to full within a second. Not one empty end was sent.

A 3 s game-thread stall (the thread suspended, the XR frame loop running) is held as a repeat of the last picture on
every cycle: 0 resubmits and 0 empty ends. The 1 s limit is reached only when the GPU finishes no frame for more than
a second.

## What went in

- **kMaxHoldNs 10 s** (rust/crates/cvr-xr/src/resubmit.rs, MAX_HOLD_NS): as the PR argues, under SteamVR with Steam
  Link a held, reprojected picture recovers the moment new frames come, while a run of empty ends resets the stream.
- **Not the third frame.** The measurements show nothing left for it to recover. The Rust capture pool has 3 slots
  (newest, previous, the one being written), so the older frame would need a fourth one of the full eye size. That is
  the extra memory the PR's four-slot C++ pool avoided.
- **Found on the way:** SteamVR's null driver had no session at all since main's 1cba63ec0 (#186). Its D3D12
  requirements name the adapter LUID 0, and the adapter check refused it. Fixed in a0d1a1396: LUID 0 names no adapter,
  so the session binds the game's.
