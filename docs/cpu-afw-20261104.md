# CPU under engine stereo and AFW (2026-11-04)

ManualSave-491 (H10 street), OpenXR simulator, RTX 5070 Ti, 16 workers. Tools: `tools/hitch_tests/hitch_profiler.py`
(frames, stack samples), `node_timeline.py` + `gtframe.py` (game thread frame), `worldtick_serial.py` (jobs inside the
world tick), the Lua host's own reports (`[lua] onUpdate over 30 s`, `CVR_LUA_PROFILE=1` for lines, game calls and
files).

## What limits the frame

| launch | GPU | limit | FPS before -> after this work |
|---|---:|---|---|
| engine stereo | 96-98 % | the GPU: the Present node waits for a frame slot (3.4 ms a frame running alone) | 63.7 -> 65.0-65.6 (p90 20.4 -> 18.8-19.2 ms) |
| AFW (`xr_afw=1`) | 55-58 % | the game thread: the world tick, ~11 ms, plus the Lua mods' onUpdate before it | 64.9 -> 67.5 (two runs; median 15.23 -> 14.61-14.64 ms, p90 19.04 -> 18.22-18.31) |

Under engine stereo CPU work removed lowers CPU load but cannot raise the frame rate: the GPU is the limit.

**AFW does unload the CPU, the render side of it:** the render graph's worker time (SceneDrv) is 22.9 ms a frame
against 37.4 ms under engine stereo (-39 %), and render nodes are idle 8.2 ms of a 14.4 ms frame. The frame rate
barely follows because the limit is the game's world tick: 0-5 ms the workers are saturated (animation, scene
collection, and the previous frame's render jobs), 5-11 ms chains of animation, streaming, physics and audio with
2-8 workers busy. Only the Lua onUpdate before it is the port's.

## What was cut

- Lua onUpdate mean 2.6 -> 1.79 ms a tick (game thread, serial before the world tick):
  - the Swimming/Ladder overrides of the state machines' GetActionValue/IsActionJustPressed are native
    (`src/Natives/ActionReads.cpp`): they ran on the world tick's workers through the Lua lock;
  - the sandbox's path check for io.open is cached (2 ms average, 15-37 ms spikes per call before);
  - game calls from Lua build no `sol::this_environment`, `obj:Member()` resolves its handle with one metatable
    compare, a String argument is taken as it is;
  - world touch lists a device's screens natively (`VREntityComponentsOf`), Reach reads its state ids once.
  - 64-bit integers returned to Lua no longer compile a chunk each ("return <n>ull"): a builder compiled once per
    state makes them from two halves;
  - TacticalBelt shares the hips frame and the palm points within a frame, Holster/WorldMap/Belt make their names
    and slot lists once.
- VRIK forward kinematics (~30 full-rig passes a frame in the player's animation job) normalises only quaternions
  that are off unit.
- Render nodes: the glass test of the draw hook is cached per bound pipeline. The port's own code is 17-18 % of the
  render nodes' CPU, spread over ~25 per-draw helpers (stereo descriptor tracking, VRS, target handoff, retained
  geometry, cascades); none of them alone is above ~1 %.

## RenderDoc check of an AFW frame

Two consecutive AFW frames captured (`renderdoccmd inject` while `launch_to_save.py --launcher-hold` keeps the game at
its launcher, before the D3D12 device; triggered through target control), analysed with the game closed, then
deleted: each frame has ONE scene pass, the G-buffer's 4 739 draws into 1536x1661 targets (the eye's render
resolution), upscaled to the eye's 2648x2864 output; 7 249 draws, 164 dispatches and 212 clears in all. Under AFW no
frame renders both eyes, which is why the render graph's CPU drops 39 % against engine stereo.

Why the port's remaining worker-side code no longer moves the frame: every per-draw helper of the draw hook leaves on
its own atomic flag when its feature is idle (target handoff/access `observing`, preparation `Active()`, VRS
`everEnabled`, ...), ~100 ns a draw together; 2.7 ms of worker CPU a frame spread over 13+ busy workers is well under
0.1 ms of frame time, and a shared gate over the stereo helpers would risk the engine-stereo path for that.

## Left

Where the remaining time is (AFW, 2 000 Hz game-thread samples): the port's serial game-thread work is the Lua
onUpdate alone; its game calls are 0.77 ms of it, the rest the mods' own Lua and the bindings. The port's code inside
the world tick's jobs is ~1.2 ms of worker CPU a frame (VRIK the most of it) and inside the render nodes ~2.7 ms
(16 % of them, ~25 per-draw helpers): spread over 13+ busy workers, either is well under 0.1 ms of frame time.
A separate Cyber Engine Tweaks with the player's own mods (CETBridge, StreamingBugWorkaround with per-frame
onUpdate, entSpawner, RedHotTools) also runs on the game thread, outside the port.

- Per mod per tick: TacticalBelt 0.26 ms, Stereo 0.26 (its HUD panel native 0.10), Reach 0.17, Weapon 0.16,
  VRIK 0.15, Optics 0.11.
- CVRBridge (the WolvenKit MCP bridge, not the port's) polls a command file ten times a second; with the path cache
  it is no longer in the top six.
